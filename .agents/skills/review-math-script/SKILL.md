# 数学讲稿与动画配合审查

同时审查讲稿是否讲对、画面是否跟得上。以科普观众能形成正确直觉为尺度，允许适度简化，不把讲稿改成教科书，也不为了制造动态而增加动画。

默认交付审查与具体修改建议；用户同时要求修改时，继续执行已授权的修改，不重复征求许可。

## 取得依据

1. 确认文字稿与目标 `projects/<name>`。读取仓库和子项目适用的 `AGENTS.md`。项目不明确时先从稿件中的对象、Scene 名称定位；仍不能确定才询问。没有稿件时请求稿件，不凭动画代写一份再自审。
2. 按论述转折划分讲稿段落，保留原句、段号或时间码。读取目标项目的 Scene 注册表、相关组件、动画状态与样式；按需追踪共享组件与时间线，不能只看 Scene 名称或摘要。
3. 建立“讲稿段落 → Scene 源文件 → 观众步骤 → 当前可见对象与变化”的对应关系。区分源码零基 `step` 与观众第几步。每段都纳入核对，输出时可合并配合良好的连续段落。
4. 使用项目现有启动与检查方式，实际播放涉及的步骤和过渡，再对照讲稿读一遍；看清动画开始、运动过程、结束停留及下一次按键的衔接。截图只能证明单个状态。缺少播放条件时继续源码审查，并把节奏、流畅度明确列为待实播验证。

## 第一方面：数学、逻辑与表达

| 分类 | 判断标准 | 处理 |
| --- | --- | --- |
| 必须修正 | 事实错误、算错、推理不成立、把特殊情况推广成一般结论，或类比使核心概念变义 | 引用原句，说明错在哪里，给出最小修正 |
| 建议优化 | 结论正确，但指代、顺序、重复或抽象措辞明显增加理解成本 | 给出更短或更直观的替换句，说明收益 |
| 可保留的简化 | 省略证明或技术条件，在当前语境中仍导向正确理解 | 保留，不凑问题清单 |

核对具体数值、定义的使用范围、前后对象身份及“因此”是否真由前文推出。必要时用计算或反例验证；不确定的事实核查可靠来源，未证实的疑点不写成已确认错误。

改写保留原段的教学意图。例如把“任意函数由两个单价决定”修正为“在这个二维空间里，一个线性泛函由它在两个基向量上的取值决定”；若前文已建立收银台类比，可说“这里任意一个线性收银台，都由两种基袋的价格决定”。不能只改成一次水果算账而丢掉“确定整个线性泛函”的关键结论。

不要求每个类比立即补齐完整定义；只有省略会影响当前结论或让观众形成错误概念时才提出。表达建议优先保留作者口吻和已有具体例子，不无故重写全文。

## 第二方面：画面能否承接讲述

内容同题不等于节奏配合。逐段检查：

- 讲到某个对象时，它是否已出现且可辨认？“这个”“这里”是否有明确视觉落点？
- 讲到交换、分解、缩放、映射、抵消或换基时，画面是否展示该过程，而不只是替换最终公式？对象身份、颜色和数学含义是否连续？
- 新结果是否过早出现？讲述是否还没到，动画已经结束？相反，话已讲完是否仍需等待无关运动？
- 同一静止画面上是否连续引入新的对象、关系或推论，却没有可指认的视觉依据？重点找这种“讲述向前，画面没跟上”的区间。

静止本身不是问题：读数、观察比较、复述当前关系和留出思考时间，可以停住。没有音频或时间码时，只标注可能的长停留及依据，不编造精确秒数，也不设置统一的静止时长上限。

对需要改进的段落，在以下方式中选最小有效调整：

1. 调整现有步骤触发点，或依次强调当前画面中正在讲的对象。
2. 将同一教学目标拆成更细的步骤，让图形真正执行对应变化。
3. 修改或补充一个必要的具体例子、对照状态或图形。
4. 若延伸是本段关键内容，为它补足画面；若只是旁支，建议压缩或移到后文，并说明取舍。
5. 只有出现独立教学目标时才建议新增 Scene，不把每句话拆成新 Scene。

每项动画建议写清：**原句触发点 → 现有 Scene/步骤 → 保留什么对象 → 哪个对象如何变化 → 最后停在哪个状态 → 帮助理解什么关系**。区分建议新增的步骤与已存在的步骤。

遵循项目极简、固定 16:9、按键推进、KaTeX 和数学几何规范。优先图形动作，不把讲稿搬成屏幕文字，不用循环闪烁或装饰运动填满停顿。检查新增内容是否挤占字幕安全区。具体步数和组件用法以当前源码及适用规范为准，发现冲突时说明，不机械套旧模板。

## 交付方式

先简述整体判断：有无硬伤、主要配合问题、核验范围（源码 / 实播 / 音频）。然后按重要性给出：

1. **必须修正**：原句位置、原因或验证依据、最小替换句。没有则明确“未发现逻辑或数学硬伤”。
2. **讲稿—画面对照**：用紧凑表格列出段落、实际 Scene/步骤、当前表现、判断及具体调整。良好段落简写；问题段落提供源码链接与动作建议。
3. **表达优化**：只列有明确收益的改写；与前两项重复的内容合并。
4. **最小修改顺序**：优先列出最影响理解的少量动作，并指出尚待验证的项目。

不要把可选优化写成阻塞交付的问题，也不要为凑数量制造缺陷。默认不改项目文件。若已获修改授权，按仓库要求完成相应构建、数学和视觉验收，再报告实际修改与验证结果。
