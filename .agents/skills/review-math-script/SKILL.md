# 数学讲稿审查

以“是否误导理解”为尺度，检查数学逻辑、表达及画面支撑。允许科普简化，保留作者口吻和教学意图，不把讲稿改成教科书。

不审查口播节奏、气口、停顿时长、音画同步或动画触发时机；这些由用户后期处理，也不列为待验证项。

## 取得依据

1. 确认稿件与目标 `projects/<name>`，读取适用的 `AGENTS.md`。先从稿件定位项目，仍不明确才询问；没有稿件时请求提供，不代写后自审。
2. 保留原句、段号或时间码，逐段对应实际 Scene 源文件、观众步骤及可见对象。读取注册表、相关组件与状态，不能只凭 Scene 名称判断；区分零基 `step` 与观众步数。
3. 涉及动态过程是否正确呈现时，实际播放核验；截图仅证明单个状态。无法播放则继续源码审查，明确哪些视觉判断尚未验证。

## 审查重点

- **数学与逻辑**：核对数值、定义范围、推理、对象身份及类比。必要时用计算、反例或可靠来源验证，不把未证实的疑点写成错误。
- **表达**：只建议能减少歧义或明显降低理解成本的改写。省略证明或技术条件若不影响当前结论，可保留，不凑问题清单。
- **画面支撑**：讲述的对象和关系是否有可辨认的视觉依据？交换、分解、缩放、映射或换基是否正确呈现，对象、颜色与数学含义是否一致？重点指出关键推论缺少画面支撑的地方，不因画面静止或停留较长就建议增加动画。

改写须保留关键结论。例如“任意函数由两个单价决定”可改为“这里任意一个线性收银台，都由两种基袋的价格决定”，不能退化成一次水果算账而丢掉“确定整个线性泛函”的意思。

画面建议采用最小有效调整，写清：**对应原句 → 现有 Scene/步骤 → 对象如何变化及结果 → 支撑什么关系**。区分已有与建议新增步骤；只有独立教学目标才建议新增 Scene。遵循项目极简、16:9、KaTeX 与字幕安全区规范，不把讲稿搬上屏幕。

## 交付

先说明整体判断与核验范围，再按重要性列出：

1. **必须修正**：原句位置、依据与最小替换句；没有则明确“未发现逻辑或数学硬伤”。
2. **画面支撑问题**：对应 Scene/步骤、源码链接及具体调整；配合良好的段落可合并简述，不必展开完整对照表。
3. **表达优化**：仅列有明确收益且不与前项重复的建议。

默认只审查、不改项目文件。用户同时要求修改时直接执行，按适用仓库规范验收并报告结果；可选优化不作为交付阻塞项。
